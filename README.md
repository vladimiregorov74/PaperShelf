# PaperShelf

**PaperShelf** — настольное приложение для сохранения, организации и чтения технических статей из Интернета.

Приложение загружает статью по URL, извлекает основное содержимое страницы, сохраняет локальную копию и предоставляет удобный интерфейс для дальнейшего чтения.

Главная особенность PaperShelf — **автоматический анализ структуры новых сайтов**. Вместо создания отдельного парсера для каждого источника приложение способно исследовать HTML страницы, определить контейнер статьи, найти необходимые элементы и сгенерировать конфигурацию селекторов.

---

## Возможности

### 📥 Сохранение статей

* сохранение статьи по URL;
* извлечение основного содержимого страницы;
* сохранение локальной копии;
* сохранение исходного URL;
* сохранение автора и источника;
* сохранение даты добавления;
* просмотр сохранённой статьи без повторной загрузки;
* открытие оригинальной статьи в браузере;
* открытие каталога статьи.

### 📚 Библиотека

* список сохранённых статей;
* поиск по названию, автору и источнику;
* сортировка по дате;
* сортировка по названию;
* переименование статей;
* удаление статей;
* автоматическое выделение только что сохранённой статьи;
* обновление библиотеки.

### 🌐 Поддержка различных сайтов

PaperShelf использует конфигурационный подход к поддержке источников.

Для сайта могут храниться:

* домен;
* селектор контейнера статьи;
* селекторы автора;
* правила очистки ненужных элементов;
* название источника;
* суффикс заголовка.

Благодаря этому для каждого сайта не требуется создавать отдельный Python-класс парсера.

Обработкой статьи занимается единый `GenericParser`, которому передаётся соответствующая конфигурация.

# Автоматический анализ сайтов

Одной из ключевых особенностей PaperShelf является возможность **автоматически добавить поддержку нового сайта**.

Если пользователь пытается сохранить статью с неизвестного источника, приложение может предложить выполнить анализ страницы.

Процесс выглядит следующим образом:

```text
URL статьи
    │
    ▼
Загрузка страницы
    │
    ▼
SiteInspector
    │
    ├── анализ DOM
    ├── поиск кандидатов статьи
    ├── оценка кандидатов
    ├── поиск автора
    └── поиск элементов для очистки
    │
    ▼
Analysis Report
    │
    ▼
SelectorGenerator
    │
    ▼
Конфигурация сайта
    │
    ├── selectors.py
    └── site_registry_data.py
    │
    ▼
GenericParser
    │
    ▼
Сохранение статьи
```

## Site Inspector

`SiteInspector` анализирует структуру загруженной страницы и пытается определить наиболее подходящий контейнер статьи.

При анализе учитываются различные характеристики DOM:

* объём текстового содержимого;
* количество дочерних элементов;
* наличие заголовков;
* изображения;
* таблицы;
* ссылки;
* блоки кода;
* структура вложенности;
* соотношение полезного и служебного содержимого.

Кандидаты получают оценку, после чего выбирается наиболее вероятный контейнер статьи.

Дополнительно анализатор определяет элементы, которые следует удалить из найденного контейнера.

Например:

```text
Статья
├── основной текст
├── заголовки
├── изображения
├── код
├── таблицы
├── реклама              ← удалить
├── навигация            ← удалить
├── блок рекомендаций   ← удалить
└── служебные элементы  ← удалить
```

Результатом работы `SiteInspector` является структурированный отчёт анализа.

# Генерация селекторов

После анализа страницы `SelectorGenerator` преобразует результаты `SiteInspector` в конфигурацию, которую сможет использовать `GenericParser`.

Сгенерированная конфигурация содержит необходимые CSS-селекторы и правила обработки страницы.

Таким образом:

```text
HTML
 │
 ▼
SiteInspector
 │
 ▼
кандидат статьи
 │
 ▼
SelectorGenerator
 │
 ▼
CSS selectors
 │
 ▼
GenericParser
```

Это позволяет отделить **анализ структуры сайта** от **последующего извлечения статей**.

Если структура сайта изменяется, существующую конфигурацию можно удалить и выполнить анализ заново.

# Динамические сайты

Современные сайты часто формируют содержимое с помощью JavaScript.

В таких случаях обычной HTTP-загрузки HTML может быть недостаточно.

PaperShelf предусматривает загрузку динамических страниц через Chromium с использованием Playwright.

При этом загрузчик не должен быть привязан к конкретному сайту или заранее известному CSS-селектору.

Для определения готовности страницы используются общие признаки:

* `DOMContentLoaded`;
* ожидание затихания сетевой активности;
* отслеживание изменений DOM через `MutationObserver`;
* ожидание периода стабильности DOM;
* полная прокрутка страницы для активации lazy loading;
* повторное ожидание стабильности DOM после прокрутки.

Упрощённо:

```text
Chromium
   │
   ▼
DOMContentLoaded
   │
   ▼
Network Idle
   │
   ▼
DOM Quiet
   │
   ▼
Scroll Through Page
   │
   ▼
DOM Quiet
   │
   ▼
page.content()
   │
   ▼
SiteInspector / Parser
```

Такой подход позволяет работать с различными JavaScript-сайтами без добавления специальных ожиданий для каждого отдельного источника.

# Архитектура

Проект построен с разделением ответственности между пользовательским интерфейсом, контроллерами, сервисами, загрузчиками и парсерами.

Основной принцип взаимодействия:

```text
UI
 │
 ▼
Controller
 │
 ▼
Service
 │
 ├── Loader
 ├── Parser
 ├── Site Inspector
 └── Storage
```

## GUI

Графический интерфейс построен на **PySide6**.

Основные компоненты:

* `MainWindow`;
* `LibraryPanel`;
* `LibraryWidget`;
* `PreviewWidget`;
* `LogWidget`;
* панели управления;
* диалоги;
* настройки;
* управление поддерживаемыми сайтами.

UI отвечает за отображение информации и взаимодействие с пользователем.

Основная бизнес-логика вынесена из Qt-виджетов в контроллеры и сервисы.

---

## Controllers

Контроллеры координируют взаимодействие между интерфейсом и прикладной логикой.

### `SaveController`

Управляет процессом сохранения статьи:

* принимает URL;
* запускает Worker;
* передаёт результаты интерфейсу;
* обрабатывает ошибки;
* управляет жизненным циклом фонового потока.

### `LibraryController`

Предоставляет интерфейсу операции над библиотекой:

* загрузка;
* сортировка;
* поиск;
* переименование.

### `SiteSupportController`

Управляет автоматическим добавлением поддержки нового сайта:

* запускает анализ;
* управляет Worker;
* обрабатывает результаты;
* передаёт ошибки интерфейсу.

# Services

Сервисы содержат прикладную логику и скрывают детали реализации от UI.

Основные сервисы:

### `ArticleService`

Работает с сохранёнными статьями:

* проверяет существование статьи;
* открывает статью;
* удаляет статью;
* открывает каталог статьи.

### `LibraryService`

Управляет библиотекой:

* загрузка;
* сортировка;
* поиск;
* переименование.

### `LibraryScanner`

Сканирует каталог библиотеки и формирует список `LibraryItem`.

### `LibraryMetadataService`

Работает с метаданными сохранённых статей.

### `SiteSupportService`

Отвечает за автоматическое добавление поддержки нового источника:

```text
URL
 ↓
Loader
 ↓
SiteInspector
 ↓
Analysis Report
 ↓
SelectorGenerator
 ↓
SiteRegistryGenerator
 ↓
Registry
```

### `SiteRegistryService`

Предоставляет доступ к зарегистрированным источникам.

### `SiteRegistryEditor`

Позволяет изменять реестр поддерживаемых сайтов, в том числе удалять существующую конфигурацию.

# Parsers

Архитектура парсеров построена вокруг общего интерфейса.

```text
BaseParser
    │
    ▼
GenericParser
    │
    ▼
Site Configuration
```

`ParserFactory` определяет, существует ли конфигурация для URL.

Если подходящая конфигурация найдена, создаётся `GenericParser`.

Таким образом, приложение не содержит отдельный класс:

```text
HabrParser
NotionParser
MediumParser
...
```

Вместо этого используется единый механизм:

```text
URL
 ↓
ParserFactory
 ↓
Site Registry
 ↓
GenericParser
 ↓
Selectors
 ↓
Article
```

Это упрощает добавление новых источников и уменьшает количество специализированного кода.

---

# Workers и QThread

Длительные операции выполняются в отдельных потоках Qt.

В частности:

* загрузка и сохранение статей;
* анализ новых сайтов;
* регистрация поддержки источников.

Используется базовый `BaseWorker`, предоставляющий общий механизм:

* запуска операции;
* журналирования;
* обработки ошибок;
* передачи исключений;
* завершения Worker;
* освобождения ресурсов.

Контроллер управляет жизненным циклом `QThread` и Worker.

Это позволяет выполнять длительные операции, не блокируя пользовательский интерфейс.

---

# Обработка ошибок

В проекте используется собственная иерархия исключений:

```text
PaperShelfError
│
├── UnsupportedSiteError
├── SiteAnalysisError
├── DynamicSiteError
└── EmptyPageError
```

Специальные исключения позволяют отделить ожидаемые ситуации от неожиданных ошибок программного кода.

Например:

`UnsupportedSiteError` сообщает приложению, что для URL отсутствует конфигурация сайта.

`SiteAnalysisError` используется, если автоматический анализ не смог определить структуру статьи.

`DynamicSiteError` предназначено для случаев, когда содержимое страницы требует специальной динамической загрузки.

# Библиотека

Каждая статья хранится в отдельном каталоге.

Пример:

```text
saved/
└── article-directory/
    ├── article.html
    └── article.json
```

Метаданные статьи хранятся отдельно от HTML.

Пример:

```json
{
    "title": "Название статьи",
    "author": "Автор",
    "source": "Habr",
    "url": "https://example.com/article",
    "created_at": "2026-08-27T15:30:00"
}
```

Название статьи может быть изменено после сохранения.

При этом исходный URL и содержимое статьи остаются неизменными.

# Управление поддерживаемыми сайтами

В PaperShelf существует отдельный раздел:

**Настройки → Поддерживаемые сайты...**

Он показывает зарегистрированные источники и позволяет удалить конфигурацию сайта.

Это особенно важно, если сайт изменил HTML-разметку.

Например:

```text
Сайт изменил структуру
        │
        ▼
Старые селекторы больше не работают
        │
        ▼
Настройки
        │
        ▼
Поддерживаемые сайты...
        │
        ▼
Удалить поддержку сайта
        │
        ▼
Повторить скачивание
        │
        ▼
Автоматический анализ
        │
        ▼
Новые селекторы
```

Таким образом, пользователю не требуется вручную редактировать CSS-селекторы.

В настоящее время учитываются:

* название статьи;

PaperShelf содержит встроенный журнал работы приложения.

В журнал выводятся:

* этапы загрузки;
* URL;
* создание и закрытие компонентов;
* операции сохранения;
* результаты анализа;
* ошибки;
* исключения;
* операции с библиотекой.

Также предусмотрена возможность включения записи журнала в файл через настройки приложения.
По умолчанию режим записи выбран - перезапись (LOG_RECORD_FLAG = "w" в papershelf/config/constants.py)
